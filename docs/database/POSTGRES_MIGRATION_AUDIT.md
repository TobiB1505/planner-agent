# PostgreSQL-Migration – Bestandsaufnahme (Audit)

Stand: Beginn des Sprints „Supabase Foundation & SQLite → PostgreSQL".
Diese Datei ist die **Bestandsaufnahme vor der ersten Codeänderung** (Sprint-Punkt 1)
und bleibt danach als Nachweis erhalten, was tatsächlich vorgefunden wurde.

Grundlage: repositoryweite Suche nach `sqlite3`, `sqlite3.connect`, `PRAGMA`,
`COLLATE NOCASE`, `INSERT OR IGNORE`, `INSERT OR REPLACE`, `AUTOINCREMENT`,
`lastrowid`, `VACUUM`, `VACUUM INTO`, `row_factory`, `sqlite3.Row`, `?`-Platzhaltern
sowie allen direkten SQL-Ausführungen (`conn.execute` / `conn.executemany` /
`executescript`).

### Löschabhängigkeiten (Ist-Verhalten, alles manuell im Code)

SQLite erzwingt Fremdschlüssel **nur**, wenn `PRAGMA foreign_keys=ON` gesetzt ist –
das passiert im Projekt **nirgends**. Die deklarierten `REFERENCES` sind heute also
reine Dokumentation. Das tatsächliche Verhalten ergibt sich ausschließlich aus dem
Anwendungscode:

| Operation | Reihenfolge im Code | Entspricht |
| --- | --- | --- |
| `db.delete_week_plan` | `assignments` → `absences` → `week_plans` | `ON DELETE CASCADE` für beide Kinder |
| `db.delete_artist_plan` | `artist_plan_entries` → `artist_plans` | `ON DELETE CASCADE` |
| `db.delete_rehearsal_plan` | `rehearsal_people` → `rehearsals` → `rehearsal_plans` | `ON DELETE CASCADE` (2 Ebenen) |
| `db.upsert_rehearsal_plan` | löscht `rehearsal_people` + `rehearsals` des Plans, baut neu auf | `ON DELETE CASCADE` |
| `db.upsert_artist_plan` | löscht `artist_plan_entries` des Plans, baut neu auf | `ON DELETE CASCADE` |
| `db.delete_person` | **Soft-Delete** (`active=0, deleted=1`) + `DELETE FROM employee_statistics` | `people` wird nie hart gelöscht → `RESTRICT` ist für alle `people`-Kinder unschädlich |
| `routers/plans.plan_save` (Update-Zweig) | löscht `assignments` + `absences` der Woche, schreibt neu | – |

`plan_audit_log.week_plan_id` und `recommendation_history.week_plan_id` werden beim
Löschen einer Woche **nicht** mitgelöscht – die Zeilen bleiben mit einer dann
verwaisten ID stehen. Das ist heute möglich, weil SQLite nichts erzwingt.

> **Konsequenz für die Migration (Sprint-Punkt 10):** Fremdschlüssel mit
> `ON DELETE CASCADE` dort, wo der Code heute schon kaskadiert. Für
> `plan_audit_log` / `recommendation_history` ist `ON DELETE SET NULL` die einzige
> Variante, die das heutige Verhalten (Zeile bleibt erhalten) beibehält, ohne dass
> `DELETE FROM week_plans` künftig fehlschlägt. Beides ist unten in Abschnitt 5
> begründet.

## 3. Mapping-Tabelle SQLite → PostgreSQL

| SQLite | PostgreSQL | Begründung / Prüfung |
| --- | --- | --- |
| `INTEGER PRIMARY KEY AUTOINCREMENT` | `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` | `BY DEFAULT` (nicht `ALWAYS`), damit die Datenmigration bestehende IDs explizit einsetzen kann. Sequenzen werden danach auf `MAX(id)` gesetzt. |
| `TEXT` (Datum `YYYY-MM-DD`, Zeit `HH:MM`) | `TEXT` | **Bewusst kein `date`/`time`.** Der gesamte Fachcode vergleicht, sortiert und serialisiert ISO-Strings (`date.fromisoformat`, `BETWEEN ? AND ?`, JSON-Response). Ein Typwechsel wäre eine API-Änderung (Sprint-Punkt 8/36 verbieten das). |
| `INTEGER` als Bool (`active`, `deleted`, `end_inferred`, `editable`, `accepted`) | `INTEGER` | Der Code schreibt `1`/`0` und liest `bool(...)`. `boolean` würde `dict(row)`-Responses von `1` auf `true` ändern → API-Änderung. |
| `REAL` (`confidence`, `score`) | `DOUBLE PRECISION` | Direktes Äquivalent. |
| `TEXT DEFAULT CURRENT_TIMESTAMP` | `TEXT DEFAULT to_char(now() AT TIME ZONE 'utc', 'YYYY-MM-DD HH24:MI:SS')` | SQLite liefert `CURRENT_TIMESTAMP` als **String** `'YYYY-MM-DD HH:MM:SS'` (UTC). Wird 1:1 in JSON-Responses durchgereicht (`created_at`, `updated_at`). Ein `timestamptz` würde das Antwortformat ändern. |
| `COLLATE NOCASE` (Index) | `CREATE INDEX ... ON t (lower(col))` | Funktionaler Index, wird von `lower(col) = lower(%s)` genutzt. |
| `col = ? COLLATE NOCASE` (Abfrage) | `lower(col) = lower(%s)` | Semantikunterschied bei Nicht-ASCII → siehe Abschnitt 4. |
| `INSERT OR IGNORE` | `INSERT ... ON CONFLICT (<echte UNIQUE-Spalte>) DO NOTHING` | Nur eine Fundstelle: `add_alias` → Conflict-Target `(alias)`. |
| `INSERT OR REPLACE` | – | **Kommt im Repository nicht vor.** Nichts zu ersetzen. |
| `INSERT ... ON CONFLICT(x) DO UPDATE SET c = excluded.c` | identisch | Bereits PostgreSQL-kompatible Syntax (SQLite hat sie von PostgreSQL übernommen). Nur Platzhalter tauschen. |
| `?` | `%s` | Explizit umgeschrieben, keine Laufzeit-Übersetzung, keine String-Interpolation. |
| `IN ({",".join("?" for ...)})` | `= ANY(%s)` mit Python-Liste | Entfernt das dynamische SQL-Zusammenbauen komplett. |
| `cur.lastrowid` | `INSERT ... RETURNING id` | 3 Fundstellen. |
| `PRAGMA journal_mode=WAL` | entfällt | PostgreSQL-MVCC. |
| `PRAGMA busy_timeout` | entfällt | Ersetzt durch Pool-`timeout`. |
| `PRAGMA foreign_keys` | entfällt | PostgreSQL erzwingt FKs immer. |
| `PRAGMA table_info(...)` | entfällt | Nur in `_migrate()`; ersetzt durch versionierte Migrationen. |
| `PRAGMA integrity_check` | entfällt | Kein Äquivalent im Anwendungsprozess. Health/Diagnostics melden stattdessen Server-Version + Migrationsstand. |
| `VACUUM INTO <datei>` | entfällt | Kein Anwendungs-Backup mehr. Strategie: Supabase-PITR/`pg_dump`, siehe `POSTGRES_BACKUP.md`. |
| `sqlite3.Row` | psycopg-Row-Factory mit `dict`-Basis + Positionszugriff | Erhält `row["x"]`, `row[0]`, `dict(row)`, `.keys()`. |
| `sqlite3.connect(..., check_same_thread=False)` | `ConnectionPool.connection()` | Der Thread-Wechsel zwischen FastAPI-`__enter__`/`__exit__` ist bei psycopg unproblematisch. |
| `conn.executescript(SCHEMA)` | Migrationsrunner | Kein implizites Schema mehr aus Request-Pfaden. |

## 4. Case-insensitive Verhalten – die kritischste Semantikfrage

**Betroffene Stellen (alle gefunden):**

| Ort | Abfrage | Fachliche Bedeutung |
| --- | --- | --- |
| `db.find_person_by_alias` | `people_aliases.alias = ? COLLATE NOCASE` | Alias → Person |
| `db.find_person_by_alias` | `people.name = ? COLLATE NOCASE` | Name → Person |
| `db.create_person` | `people.name = ? COLLATE NOCASE` | Reaktivierung soft-gelöschter Personen |
| `intelligence/employee_stats._current_week_statistics` | `rp.person_name = ? COLLATE NOCASE OR rp.raw_name = ? COLLATE NOCASE` | Show-Teilnahme der laufenden Woche |
| `db._nocase_fold` (Python) | `str.translate(A-Z→a-z)` | In-Memory-Pendant in `PersonLookup` |
| `routers/imports._resolve_with_choices` | `people.name = ?` **ohne** `COLLATE NOCASE` | bewusst exakt – vom Nutzer im Review-Dialog gewählter Name |

**Der entscheidende Unterschied:** SQLites `NOCASE` faltet laut Dokumentation
**ausschließlich ASCII A–Z**. `str.lower()`/PostgreSQL-`lower()` falten dagegen
volles Unicode – `'RENÉ'` → `'rené'`, `'MÜLLER'` → `'müller'`.

Der bestehende Code kennt diesen Unterschied bereits und dokumentiert ihn explizit
in `db._nocase_fold()` (mit Verweis auf echte Namen wie „René"). `PersonLookup`
bildet SQLite bewusst ASCII-only nach.

**Konsequenz:** Ein naives `lower()` in SQL würde die Auflösung *weiter* machen als
heute (`RENÉ` würde plötzlich auf `rené` treffen, was SQLite heute **nicht** tut).
Das wäre eine stille Semantikänderung an der zentralen Personenauflösung.

**Entscheidung:** Die exakte SQLite-`NOCASE`-Semantik wird in PostgreSQL über eine
ASCII-only-Faltungsfunktion nachgebildet:

```sql
CREATE FUNCTION planner_nocase(text) RETURNS text
  ... translate($1, 'ABCDEFGHIJKLMNOPQRSTUVWXYZ', 'abcdefghijklmnopqrstuvwxyz') ...
  IMMUTABLE
```

plus funktionale Indizes darauf. `translate()` ist in PostgreSQL `IMMUTABLE` und
damit indizierbar. Das ist **exakt** dieselbe Abbildung wie `db._nocase_fold()` in
Python – die beiden Auflösungswege (SQL und `PersonLookup`) bleiben dadurch
garantiert deckungsgleich, was heute schon Voraussetzung ist.

`citext` wird **nicht** verwendet: es faltet ebenfalls voll-Unicode-nah und würde
denselben Semantikbruch verursachen; außerdem müsste es pro Datenbank als Extension
installiert werden.

Zu testen (Sprint-Punkt 11): `Tobi` / `TOBI` / `tobi` treffen dieselbe Person,
`René` / `RENÉ` treffen sie **nicht** (heutiges Verhalten).

## 5. Fremdschlüssel – geplantes Verhalten und Vorab-Prüfung

Da SQLite heute nichts erzwingt, können Alt-Daten Waisen enthalten. Vor dem
Aktivieren der Fremdschlüssel prüft das Migrationstool (`--dry-run`) jede Relation:

| Relation | Geplantes `ON DELETE` | Warum |
| --- | --- | --- |
| `people_aliases.person_id → people.id` | `CASCADE` | `people` wird nie hart gelöscht; Cascade ist die konsistente Wahl |
| `assignments.week_plan_id → week_plans.id` | `CASCADE` | `delete_week_plan` löscht heute genau so |
| `assignments.person_id → people.id` | `RESTRICT` (Spalte nullable) | Personen werden nur soft-gelöscht |
| `absences.week_plan_id → week_plans.id` | `CASCADE` | wie oben |
| `absences.person_id → people.id` | `RESTRICT` | wie oben |
| `artist_plan_entries.artist_plan_id → artist_plans.id` | `CASCADE` | `delete_artist_plan` |
| `rehearsals.rehearsal_plan_id → rehearsal_plans.id` | `CASCADE` | `delete_rehearsal_plan` |
| `rehearsal_people.rehearsal_id → rehearsals.id` | `CASCADE` | `delete_rehearsal_plan` |
| `person_memory_overrides.person_id → people.id` | `CASCADE` | Person wird nie hart gelöscht |
| `employee_skills.person_id → people.id` | `CASCADE` | dito |
| `employee_memory.person_id → people.id` | `CASCADE` | dito |
| `employee_statistics.person_id → people.id` | `CASCADE` | dito |
| `plan_audit_log.week_plan_id → week_plans.id` | **`SET NULL`** | Heute bleibt der Auditeintrag beim Löschen der Woche stehen. `CASCADE` würde Audithistorie vernichten, `RESTRICT` würde `DELETE FROM week_plans` neu fehlschlagen lassen. `SET NULL` erhält den Eintrag – die Spalte ist bereits nullable und `list_events` kann auch über `start_date` filtern. |
| `recommendation_history.week_plan_id → week_plans.id` | **`SET NULL`** | gleiche Begründung |
| `recommendation_history.person_id → people.id` | `RESTRICT` | wie andere `person_id` |

**Waisen werden nicht automatisch gelöscht.** Das Tool meldet sie und bricht ab.

## 6. Offene Punkte, die dieser Sprint bewusst NICHT löst

* Supabase Auth, Rollen, RBAC, RLS (eigener Folge-Sprint).

## 7. Ergebnis der Bestandsaufnahme

Die Migration ist mit vertretbarem Risiko machbar, weil:

1. es **kein ORM** gibt und die Persistenzschicht (`backend/db.py`) eine klar
   abgegrenzte Funktions-API mit stabilen Signaturen hat;
2. die Row-Zugriffsmuster homogen sind (`row["x"]`, `dict(row)`) und über eine
   Row-Factory unverändert bedienbar bleiben;
3. `ON CONFLICT`-Upserts bereits in PostgreSQL-Syntax geschrieben sind;
4. AP10 die Transaktionsgrenzen bereits auf „die Route besitzt die Transaktion"
   gezogen hat – dieses Modell passt unverändert auf psycopg.

Die drei echten Risiken sind:

1. **`COLLATE NOCASE`-Semantik** (Abschnitt 4) – gelöst über `planner_nocase()`.
2. **Fremdschlüssel, die erstmals erzwungen werden** (Abschnitt 5) – gelöst über
   Vorabprüfung im Migrationstool.
3. **`VACUUM INTO`-Backup und `PRAGMA integrity_check`** in Health/Diagnostics/
   Startvorprüfung – haben kein Äquivalent und brauchen einen bewussten Ersatz
   statt eines stillen Wegfalls.
