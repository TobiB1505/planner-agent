## Architekturentscheidungen (`NEEDS_ARCHITECTURE_DECISION`)

Bewusst **nicht** in Sprint 0 entschieden oder umgesetzt — nur markiert, mit kurzer Empfehlung:

| Thema | Empfehlung (kurz) | Begründung |
|---|---|---|
| Vollständige Tailwind-Entfernung vs. Ausbau | Eher entfernen oder auf `@theme`-Tokens umstellen | Laut Audit nur ~5 Utilities tatsächlich genutzt, aber vollständig installiert — Build-Overhead ohne Gegenwert. Reine Bau-/Architekturfrage, keine S1-Relevanz. |
| Migration zu Tailwind (voller Umfang) | Nicht empfohlen | Würde praktisch das gesamte bestehende CSS-System ersetzen — Kernthema für ein eigenes, dediziertes Sprint-Vorhaben, nicht nebenbei. |
| Server-Component-Migration | Schrittweise für Dashboard/Team/Archiv/Planungslogik, mit `loading.tsx`/`error.tsx` je Route | Größter Performance-Hebel laut Audit (C12), aber ändert Datenfluss-Timing — nicht ohne dedizierte Testphase. |
| Vercel-spezifisches Server-Fetching | Abhängig von der Server-Component-Entscheidung | Betrifft, wie/ob das Backend von einer Vercel-Deployment-Umgebung aus erreichbar ist — siehe nächster Punkt. |
| Backend-Erreichbarkeit aus Vercel | Vor jeder Server-Component-Migration klären | Das Projekt läuft aktuell primär lokal/Desktop (`backend-supervisor.ts`, lokales SQLite) — eine Vercel-Deployment-Strategie mit Server-Fetching setzt voraus, dass das Backend von dort erreichbar ist. Ungeklärt, außerhalb des Frontend-Scopes dieses Audits. |
| Desktop-/Supervisor-Architektur | Härten (FD-Leak schließen, PID-Datei, Log-Rotation), nicht neu bauen | `lib/backend-supervisor.ts` hat laut Audit einen offenen File-Descriptor-Leak (`logFd` nie geschlossen) — Frontend-seitige Härtung ohne Backend-Eingriff möglich, aber kein S1-Datenverlustrisiko, daher nicht in Sprint 0. |
| Light-Theme entfernen oder weiterführen | Entfernen empfohlen (Audit-Position bestätigt) | `data-theme="command"` ist seit einer früheren Session hart in `layout.tsx` gesetzt, `prefers-color-scheme: dark`/Light-Defaults in `foundation.css` sind seither toter Code. Entfernen vereinfacht das Token-System für Sprint 1, ist aber eine sichtbare, wenn auch risikoarme Änderung — deshalb hier nur markiert, nicht in Sprint 0 umgesetzt. |
| Globales Redesign der Kategoriefarben | Nicht in Sprint 1 antasten, Kanten/Akzente statt Flächen erst in Sprint 2 (Editor-Ent-Excelung) | `category-colors.css`/`lib/categoryColors.ts` müssen fachlich exakt der Excel-Vorlage entsprechen (Wiedererkennungswert) — jede Änderung ist gleichzeitig ein Business-Risiko, nicht nur visuell. |
| Änderung des Exportdesigns | Nicht antasten | Explizit außerhalb jeden Sprint-Scopes laut Auftrag; der Export muss byte-identisch zur bekannten Vorlage bleiben. |
